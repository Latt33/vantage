What Is This Template?

Problem

  • Hackathons need fast iteration: idea → deployed in minutes
  • Teams waste 2–4 hours on infrastructure setup
  • Cookiecutter templates risk disqualification if code exists before the event

Solution

  • Cookiecutter template — generates fresh project at hackathon start
  • Every file is infrastructure only, annotated with TODO
  • One timestamped commit proves all code was written during the event
  • Pre-configured CI/CD deploys automatically on every push

Key Guarantee

The generated repository has exactly one commit (the generation itself). No ancestral history.

Choose Your Inference Backend

At generation time, pick the inference backend that fits your hackathon project:

CLOUD RUN

Serverless Inference

  • Docker container → Cloud Run
  • Auto-scales, pay-per-use
  • No machine management
  • Best for: lighter inference, CPU tasks, quick demos
VS
VERDA GPU

Bare Metal GPU

  • Rent a GPU machine via verda.ai
  • SSH access, your startup script
  • Next.js calls Verda machine directly via HTTP
  • Best for: heavy GPU tasks, custom NN training, large models

How It Works

The post-generate hook removes the unchosen backend from the generated repo. The result is clean — only the files relevant to your choice exist.

Choose Your Auth Provider

Pick the authentication strategy that fits your demo:

SUPABASE

Supabase Auth (Default)

No Middleman

Next.js calls the Verda GPU machine directly via HTTP. No Cloud Run, no extra hop. The machine has a public IP — it's just an HTTP server.

Why Not Supabase Edge Functions for Inference?

  • Supabase Edge Functions are stateless and time-limited (max 60s)
  • Verda inference calls can take minutes for large prompts
  • Cloud Run supports min-instances = 1 (no cold starts) + 60s timeout

CI/CD Pipeline (GitHub Actions)

Workflows

  • ci.yml — every push/PR. Lint + TypeScript + test. 5 min timeout.
  • deploy-vercel.yml — on push to dev/staging/main. Vercel pull → build → deploy.
  • deploy-cloudrun.yml — cloudrun mode only. Cloud Build → Artifact Registry → Cloud Run.
  • deploy-all.yml — orchestrated. Vercel → Cloud Run sequential.

Inference Service — Cloud Run Mode

Dockerfile (Multi-stage)

FROM node:20-alpine AS base
WORKDIR /app
FROM base AS deps
COPY package*.json ./
RUN npm ci --omit=dev
FROM base AS builder
COPY --from=deps /app/node_modules ./
COPY . . && npm run build
FROM base AS runner
ENV NODE_ENV=production
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/package*.json ./
EXPOSE 3000
CMD ["node", "dist/index.js"]

deploy-to-verda.sh (CI/CD via SSH)

# Builds image → pushes to registry
# SSHs to Verda machine → pulls → restarts
./deploy-to-verda.sh \
  --host gpu01.verda.example.com \
  --registry gcr.io/my-project

How It Works

  1. Rent a GPU machine at verda.ai
  2. Paste provision.sh into the Verda dashboard startup script field
  3. Machine boots, runs your startup script
  4. Model server starts on port 8080
  5. Next.js calls it directly: http://<verda_ssh_host>:8080
  6. Push updates via deploy-to-verda.sh (SSH)

Direct HTTP — No Middleman

The Verda machine has a public IP. Next.js calls it directly. No Cloud Run, no API key.

Why Not Prisma?

  • No schema drift between prisma schema and actual DB
  • Simpler hackathon workflow: just write SQL
